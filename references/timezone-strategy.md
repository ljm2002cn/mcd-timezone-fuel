# 时区策略参考表

本文件是 SKILL.md 中时段策略的展开说明，供开发与调优时查阅。

---

## 一、时段划分依据

划分依据是**目标时区的当地时间**（即用户实际进食行为发生时当地的钟点），而非服务器时区。

| 区间 | 标签 | 生理与行为特征 | 选品倾向 |
|---|---|---|---|
| 05:00–09:00 | 清晨 | 刚醒，胃处于唤醒初期，注意力未完全集中 | 轻负担、易消化、避免过冷；可搭配含咖啡因选项但标注摄入时段 |
| 09:00–12:00 | 上午 | 开工前/工作中，正式进食需求出现 | 标准正餐，保证饱腹 |
| 12:00–14:00 | 午间 | 午休窗口，餐后需恢复精力 | 常规午餐；优先可用券组合 |
| 14:00–17:00 | 午后 | 典型餐后困倦期（尤其高碳水后） | 低糖、高蛋白、避免大份主食；说明"为什么不是汉堡" |
| 17:00–20:00 | 傍晚 | 下班/晚餐，正式正餐 | 常规正餐，可放纵档 |
| 20:00–23:00 | 夜间 | 收尾，次日睡眠临近 | 轻食为主，控制钠摄入 |
| 23:00–05:00 | **深夜** | 熬夜/值班，次日仍有工作 | **控油控钠优先，禁止重油炸物；选能撑 3–4 小时的组合** |
| 05:00 前（跨 00:00） | 深夜偏后/倒班 | 接近或已跨日，代谢最低谷 | 最轻量；避免高咖啡因与高钠 |

## 二、典型时差组合

中国 UTC+8 出发，对应目标时区当地时刻：

| 目标时区 | 时差 | 北京 03:12 时当地 | 北京 12:00 时当地 | 北京 21:00 时当地 |
|---|---|---|---|---|
| 美东 UTC-4（纽约） | -12 | 前一日 15:12 | 00:00 | 09:00 |
| 美西 UTC-7（洛杉矶） | -15 | 前一日 12:12 | 前一日 21:00 | 06:00 |
| 中欧 UTC+1（柏林） | -7 | 前一日 20:12 | 05:00 | 14:00 |
| 英国 UTC+0（伦敦） | -8 | 前一日 19:12 | 04:00 | 13:00 |
| 东南亚 UTC+8（新加坡） | 0 | 03:12 | 12:00 | 21:00 |
| 澳东 UTC+10（悉尼） | +2 | 05:12 | 14:00 | 23:00 |

**深夜分支命中判断**：目标时区当地时间落在 23:00–05:00 即命中。

## 三、三档方案定义

| 档位 | 适用 | 选择准则 |
|---|---|---|
| **A 档 · 轻负担** | 深夜/清晨**强制**；其他时段作为保底选项 | 相对低钠、相对低脂、蛋白质占比不低、能提供持续饱腹感 |
| **B 档 · 均衡** | 日常推荐 | 常规正餐结构，营养与口味平衡，可叠加优惠 |
| **C 档 · 放纵** | 用户明确想 reward 自己 | 口味优先，但**必须明确标注代价**（热量/钠），不隐藏取舍 |

每档必须包含：
1. 餐品组合（来自 `query-meals` / `query-meal-detail`）
2. 热量与钠参考值（来自 `list-nutrition-foods`）—— 标注为「参考值」，仅用于相对比较
3. 券可用性（来自 `available-coupons` / `query-my-coupons` / `query-store-coupons`）
4. **一句话理由，必须说明为什么适合"这个时段"**（而不是泛泛描述口味）

## 四、门店差异注意事项

不同门店在售菜品、可用券、库存均不同。

- 自助点餐：拉取自己门店 `query-meals` 即可
- 跨时区代点：**必须**用目标地址对应门店的数据
  - `delivery-query-addresses` → `delivery-query-stores` → `query-meals`
- 不可套用其他门店菜单，也不可使用自己门店的券去套目标门店订单

---

## 五、券使用原则

1. 三处券源都要查：`available-coupons`（可领）、`query-my-coupons`（已有）、`query-store-coupons`（门店限定）
2. 用券后必须 `calculate-price` 官方核价，输出「原价 → 优惠 → 实付（含配送费）」
3. 若最优券组合导致超出用户预算 → 明确提示，并给出不使用该券的备选，**不为了用券而推荐多花钱**
4. 若有可领但未领取的券，在建议中提示用户可先领

## 六、边界场景处理

| 场景 | 处理方式 |
|---|---|
| 用户未说明时区 | 必须先询问，不默认 UTC+8 |
| 用户明确在"我这边凌晨" | 以用户所在地为基准，同时给出目标时区换算 |
| 深夜 + 用户在控重/健身 | A 档优先，仍给出参考值，明确不构成专业建议 |
| 深夜 + 用户要"放纵" | 给 C 档但标注代价，不说教式拒绝 |
| MCP 返回 401/403 | 如实告知无法获取实时数据，给降级路径（凭门店菜单手动选），**不用记忆中的价格冒充实时结果** |
| MCP 返回 429 | 降低调用频率，说明限流 600 次/分钟，稍后重试 |
| 用户索要疾病/孕期/婴幼儿具体建议 | 说明仅基于公开营养数据做粗略相对比较，建议咨询专业人士 |
| 用户要求代下单但地址来自他人 | 仅使用用户自己账号下已创建的地址，不代填他人信息 |

## 七、可扩展点

- 时段策略表可按地区饮食习惯扩展（如东南亚口味偏好）
- A/B/C 三档可按用户历史订单（`order-list`）做个性化加权
- 可结合 `campaign-calendar` 在特定节点（如大促日、月末）推荐限定组合
